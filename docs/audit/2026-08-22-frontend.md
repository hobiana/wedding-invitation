## Synthèse

Le front est propre dans sa structure — alias `@/`, types tous importés de `@invitation-app/shared` sans une seule redéclaration, zéro `any`, découpage composants/pages cohérent, et les commentaires de code documentent honnêtement les bugs déjà corrigés. Le problème n'est pas l'architecture, c'est la **gestion des chemins non nominaux**, et il est systémique plutôt qu'accidentel : sur les 10 `useMutation` et 7 `useQuery` de l'application, la grande majorité n'expose ni état de chargement ni état d'erreur, et **quatre des cinq pages ignorent purement et simplement le `error` de leurs `useQuery`** — une API en échec y produit un écran vide indiscernable d'une base vide. Le commentaire de `lib/api.ts:11-14` identifie précisément ce défaut mais ne le corrige que pour le cas 401 ; les 500, timeouts et coupures réseau restent silencieux.

Deux constats méritent une correction avant mise en production : le dialogue d'édition de foyer **réintroduit le bug `confirmedCount = 0`** que le commit 4f5574f avait corrigé ailleurs, sur un chemin différent et non couvert par les tests ; et l'ensemble des messages d'erreur serveur — tous rédigés en anglais côté API — remontent bruts à l'écran, y compris sur la page invité française.

Côté accessibilité, les labels de formulaire sont réellement associés partout (`htmlFor`/`id`, ou `useId`, ou `aria-label`), ce qui est rare et mérite d'être noté. En revanche la modale de foyer n'est pas une modale accessible, et le drag-and-drop du plan de table n'a pas d'alternative clavier utilisable.

## Constats

### [BLOQUANT] Le dialogue d'édition réintroduit `confirmedCount = 0` sur un foyer qui passe de PENDING à CONFIRMED

**Où :** `apps/web/src/components/HouseholdFormDialog.tsx:34` et `:50`, champ associé `:96-108`

**Constat :** l'état local `confirmedCount` est initialisé à `0` quand le foyer est `PENDING` (son `confirmedCount` vaut alors `null`). Si l'admin change le statut en `CONFIRMED` sans toucher au champ numérique — qui n'apparaît qu'après le changement de statut, déjà pré-rempli à `0` — le formulaire envoie `confirmedCount: 0` avec `status: "CONFIRMED"`.

**Preuve :**

```tsx
// HouseholdFormDialog.tsx:34 — null devient 0 dès l'ouverture du dialogue
const [confirmedCount, setConfirmedCount] = useState(initial?.confirmedCount ?? 0);

// HouseholdFormDialog.tsx:50 — la garde ne protège que le cas PENDING *sortant*
...(status !== "PENDING" && { confirmedCount: status === "DECLINED" ? 0 : confirmedCount }),

// HouseholdFormDialog.tsx:102 — min={0} autorise explicitement la valeur
min={0}
```

Le commentaire lignes 46-49 explique correctement pourquoi il ne faut pas écrire `0` sur un foyer `PENDING`, et la garde `status !== "PENDING"` traite bien ce cas. Mais elle laisse passer la transition `PENDING → CONFIRMED`, où la valeur envoyée est le `0` hérité de l'initialisation.

L'API ne rattrape pas : `apps/api/src/households/households.service.ts:47-52` ne valide que la borne haute.

```ts
const confirmedCount = dto.confirmedCount ?? household.confirmedCount;
if (confirmedCount !== null && confirmedCount > allocatedSeats) {
  throw new BadRequestException('confirmedCount cannot exceed allocatedSeats');
}
return this.prisma.household.update({ where: { id }, data: dto });
```

À comparer avec le chemin public, qui lui interdit ce cas (`apps/api/src/invitation/invitation.service.ts:63-66`) :

```ts
if (dto.confirmedCount === undefined || dto.confirmedCount < 1) {
  throw new BadRequestException('confirmedCount must be at least 1 when confirming');
}
```

Le chemin admin est donc plus permissif que le chemin public sur un invariant métier, et le front s'engouffre dedans par défaut.

Aucun test ne couvre la transition. Les cinq cas de `HouseholdFormDialog.test.tsx` sont : création, pré-remplissage, correction d'un foyer déjà `CONFIRMED`, passage à `DECLINED`, et — test de non-régression du commit 4f5574f, `:74-91` — un foyer `PENDING` qui **reste** `PENDING`. Le seul chemin non testé est précisément `PENDING → CONFIRMED`.

Le plus révélateur est le commentaire de ce test de non-régression (`HouseholdFormDialog.test.tsx:69-73`), qui décrit mot pour mot la panne que le chemin non testé provoque :

```
// Regression: a household that never answered has confirmedCount: null,
// meaning the seating maths falls back to allocatedSeats (its full
// reservation). Editing it (e.g. only to fix a typo in the name) must not
// silently overwrite that null with 0 — that would make the table planner
// think it holds zero seats instead of its full allocation.
```

Le garde-fou a été posé pour l'édition d'un foyer `PENDING` laissé `PENDING`. Il ne couvre pas le cas où l'admin fait ce pour quoi ce dialogue existe : enregistrer la réponse.

**Impact :** l'usage le plus courant du dialogue d'édition — l'organisateur saisit une réponse reçue par téléphone, ce que l'invariant 2 du domaine prévoit explicitement — produit un foyer `CONFIRMED` à 0 personne. Conséquences en cascade : `totalConfirmedGuests` du tableau de bord sous-compte (`dashboard.service.ts:38` somme les `confirmedCount`), et le calcul de capacité des tables utilise `confirmedCount ?? allocatedSeats` (`tables.service.ts:64`) — un `0` explicite l'emporte sur le `??`, donc le foyer occupe **zéro siège** dans le plan de table alors qu'il vient de confirmer sa venue. Des invités confirmés se retrouvent sans place le jour du mariage, et rien à l'écran ne le signale.

**Correction proposée :** initialiser l'état à `initial?.confirmedCount ?? initial?.allocatedSeats ?? 1` plutôt qu'à `0` (même logique que `InvitationPage.tsx:56`, qui a été corrigé dans ce sens par 4f5574f), et passer le champ à `min={1}` puisque le cas « personne ne vient » est déjà porté par le statut `DECLINED`. Défendre l'invariant côté API dans le même mouvement, pour que le front ne soit pas le seul rempart. Ajouter le test de la transition `PENDING → CONFIRMED`.

**Effort :** S

### [MAJEUR] Quatre pages ignorent le `error` de leurs `useQuery` : une API en échec produit un écran vide silencieux

**Où :** `apps/web/src/pages/admin/HouseholdsPage.tsx:15-18` · `apps/web/src/pages/admin/TablesPage.tsx:23-30` · `apps/web/src/pages/admin/DashboardPage.tsx:7-13` · `apps/web/src/pages/admin/SettingsPage.tsx:9-12`

**Constat :** ces quatre pages ne déstructurent que `data` (et, pour le tableau de bord, `isLoading`). Le champ `error` n'est jamais lu ni rendu. Comme `lib/queryClient.ts:4` fixe `retry: false`, une seule requête en échec — 500, timeout, perte de réseau — suffit à mettre la page dans un état définitif sans aucun message.

**Preuve :**

```tsx
// HouseholdsPage.tsx:15 — error jamais récupéré
const { data: households } = useQuery({ queryKey: ["households"], ... });
// puis, ligne 76, le seul rendu :
{households?.map((h) => ( ... ))}   // undefined → <tbody> vide, aucun message
```

```ts
// queryClient.ts:3-5 — aucune tentative de reprise
export const queryClient = new QueryClient({
  defaultOptions: { queries: { retry: false, refetchOnWindowFocus: false } },
});
```

Le cas du tableau de bord est le plus net, car il possède déjà les deux autres branches et l'erreur tombe dans le trou entre elles (`DashboardPage.tsx:39-51`) : `householdsLoading` est `false`, et `households?.length === 0` vaut `undefined === 0` donc `false`. Aucune des deux lignes de repli ne s'affiche : le tableau est intégralement vide, sans un mot.

`SettingsPage` produit une variante plus dure encore (`SettingsPage.tsx:13-26`) : `form` n'est alimenté que par le `useEffect` sur `data`, donc en cas d'erreur il reste `null` et la page affiche **« Chargement… » indéfiniment**.

Ce défaut est connu de l'équipe — `lib/api.ts:11-14` le décrit mot pour mot :

```
 * Any other 401 means an admin's session expired mid-use. Without this, every
 * later call failed into a React Query error state that pages render the same
 * as "no data yet" — a silently empty admin screen.
```

La parade mise en place ne couvre que le 401. Les 500, les timeouts et le mode hors ligne restent exactement dans l'état décrit.

**Impact :** l'organisateur ouvre « Foyers » pendant que l'API redémarre et voit une liste vide. Rien ne distingue « la requête a échoué » de « il n'y a aucun foyer ». Le risque concret est qu'il conclue à une perte de données et recrée des foyers déjà existants, ce qui génère de nouveaux `linkId` et invalide les liens déjà envoyés aux invités. Sur la page Paramètres, il attend devant un chargement qui n'aboutira jamais.

**Correction proposée :** rendre l'état d'erreur obligatoire sur chaque `useQuery`. Le plus économique est un petit composant partagé (`<QueryState query={...}>` ou un `ErrorBoundary` par route) qui traite les trois cas chargement / erreur / vide, et un bouton « Réessayer » câblé sur `refetch()`. Envisager `retry: 1` par défaut plutôt que `false`, au moins pour les requêtes en lecture.

**Effort :** M

### [MAJEUR] Les messages d'erreur de l'API, tous en anglais, remontent bruts à l'écran — y compris sur la page invité

**Où :** `apps/web/src/lib/api.ts:36` (source) · `apps/web/src/pages/InvitationPage.tsx:46-50` (page invité) · `apps/web/src/pages/admin/TablesPage.tsx:116` · `apps/web/src/pages/admin/HouseholdsPage.tsx:61` · `apps/web/src/pages/admin/SettingsPage.tsx:74-76`

**Constat :** `request()` construit l'`Error` à partir du `message` du corps de réponse, et cinq points de rendu affichent ce message tel quel.

**Preuve :**

```ts
// api.ts:35-36
const body = await res.json().catch(() => ({}));
throw new Error(body.message ?? `Request failed with status ${res.status}`);
```

```tsx
// InvitationPage.tsx:46-50 — page invité, en français
{rsvpMutation.isError && (
  <p className="text-sm text-red-600">
    {rsvpMutation.error instanceof Error ? rsvpMutation.error.message : "Une erreur est survenue."}
  </p>
)}
```

Les chaînes que l'API produit sur ce chemin précis, relevées dans le code serveur :

| Origine | Message affiché |
|---|---|
| `invitation.service.ts:65` | `confirmedCount must be at least 1 when confirming` |
| `invitation.service.ts:70` | `confirmedCount cannot exceed allocatedSeats` |
| `tables.service.ts:92` | `Table "Table 3" only has 2 seat(s) left, this household needs 4` |
| `households.service.ts:50` | `confirmedCount cannot exceed allocatedSeats` |
| `api.ts:36` (repli) | `Request failed with status 500` |

Le repli anglais de la ligne 36 est lui-même affiché en toutes lettres à l'invité dès que la réponse n'a pas de corps JSON — ce qui est le cas d'un 502 de reverse proxy ou d'une coupure côté passerelle.

Deuxième défaut sur la même ligne : le `ValidationPipe` de NestJS renvoie `message` sous forme de **tableau** de chaînes. `new Error(["a","b"])` produit le message `"a,b"` — l'invité verrait une liste de contraintes anglaises concaténées par des virgules.

La garde `rsvpClosed` de `InvitationPage.tsx:30` réduit le risque sur le cas deadline, mais ne l'élimine pas : elle compare l'horloge du téléphone à la deadline, et la donnée `wedding` peut dater de plusieurs minutes. Un invité qui ouvre sa page juste avant l'échéance et valide juste après reçoit le 403 et son message anglais.

**Impact :** violation directe de la règle de langue du domaine (« l'interface invité est en français, sans exception ») sur la seule page que l'invité verra jamais. Au-delà de la langue, ces messages sont des chaînes de développeur : `confirmedCount cannot exceed allocatedSeats` n'indique à personne quoi corriger. Côté admin, le message de capacité est le seul retour du 409, donc l'organisateur perd aussi l'information utile qu'il contient (le nombre de places restantes).

**Correction proposée :** faire porter à l'erreur son `status` HTTP et un code stable, plutôt que la seule chaîne serveur — par exemple une classe `ApiError { status, code, message }` levée par `request()`. Le front associe alors chaque `status`/`code` à un texte français (`403` sur le RSVP → « Les réponses sont closes… », `409` sur l'assignation → « Il ne reste que N places à cette table »), avec un message générique français par défaut. Le message brut de l'API ne doit jamais atteindre un `<p>`.

**Effort :** M

### [MAJEUR] Huit mutations sur dix n'ont aucun état de chargement : double soumission possible sur réseau lent

**Où :** `apps/web/src/pages/InvitationPage.tsx:18-21` + `apps/web/src/components/RsvpForm.tsx:60-65` · `apps/web/src/pages/admin/TablesPage.tsx:38-76` · `apps/web/src/pages/admin/HouseholdsPage.tsx:20-53` + `HouseholdFormDialog.tsx:114` · `apps/web/src/pages/LoginPage.tsx:52`

**Constat :** l'application compte 10 `useMutation`. `isPending` n'en garde que **deux** : `updateTable` (`TablesPage.tsx:141`, bouton Enregistrer de l'édition de table) et `updateMutation` de `SettingsPage` (`:71` et `:86`). Pour les huit autres, le bouton reste actif pendant tout le vol de la requête, sans indicateur.

**Preuve :**

```
$ grep -rn "isPending" apps/web/src
apps/web/src/pages/admin/SettingsPage.tsx:71:        <Button type="submit" disabled={updateMutation.isPending}>
apps/web/src/pages/admin/SettingsPage.tsx:86:          disabled={updateMutation.isPending}
apps/web/src/pages/admin/TablesPage.tsx:141:                    disabled={!editing.name || updateTable.isPending}
```

Deux mutations gardées sur dix. Ne sont notamment pas couverts — et ce sont les plus exposées :

```tsx
// RsvpForm.tsx:61 — le bouton du parcours invité, jamais désactivé
<Button type="submit">Je viens</Button>
// le composant ne reçoit même pas de prop permettant de le désactiver :
interface RsvpFormProps { allocatedSeats; defaultConfirmedCount?; defaultDietaryNotes?; onSubmit; }
```

```tsx
// TablesPage.tsx:108-113 — création de table, désactivé sur le nom vide seulement
<Button onClick={() => createTable.mutate({ ... })} disabled={!newTableName}>
```

```tsx
// HouseholdsPage.tsx:100 — suppression, aucune garde
<Button variant="destructive" size="sm" onClick={() => deleteMutation.mutate(h.id)}>
```

**Impact :** c'est précisément le scénario « téléphone moyen, 4G faible » du parcours invité. Rien ne se passe visiblement après le clic sur « Je viens » : l'invité reclique. Chaque clic est un `PATCH` supplémentaire — ici idempotent, donc sans corruption, mais l'invité n'a toujours aucun retour et peut abandonner en croyant que sa réponse n'est pas partie. Côté admin le double clic n'est pas idempotent : deux clics sur « Ajouter une table » créent deux tables, deux clics sur « Enregistrer » du dialogue créent deux foyers — donc deux `linkId` pour la même famille.

**Correction proposée :** ajouter une prop `isSubmitting` à `RsvpForm` et à `HouseholdFormDialog`, la câbler sur `mutation.isPending`, désactiver le bouton et changer son libellé (« Envoi… »). Sur les pages admin, désactiver systématiquement le déclencheur pendant `isPending`. Le libellé textuel importe : un simple `disabled` ne se perçoit pas au lecteur d'écran comme une progression.

### [MAJEUR] La modale d'édition de foyer n'est pas une modale accessible : pas de rôle, pas de piège de focus, pas d'Échap

**Où :** `apps/web/src/components/HouseholdFormDialog.tsx:54-56` et `:112-115`

**Constat :** le dialogue est une `<div>` en `fixed inset-0` contenant un `<form>`. Aucun `role="dialog"`, aucun `aria-modal`, aucun `aria-labelledby` pointant vers le titre de la ligne 57, aucune gestion de la touche Échap, aucun déplacement du focus à l'ouverture ni de restauration à la fermeture, aucun confinement du focus, et le fond semi-transparent ne se ferme pas au clic.

**Preuve :**

```tsx
// HouseholdFormDialog.tsx:54-57
<div className="fixed inset-0 bg-black/40 flex items-center justify-center">
  <form onSubmit={handleSubmit} className="bg-white rounded-lg p-6 w-full max-w-sm space-y-4">
    <h2 className="text-lg font-semibold">{isEdit ? "Modifier le foyer" : "Nouveau foyer"}</h2>
```

Le contenu sous-jacent n'est pas non plus rendu inerte : `HouseholdsPage.tsx:109-123` monte le dialogue en frère du tableau, sans `aria-hidden` ni `inert` sur ce dernier.

**Impact :** à l'ouverture, le focus reste sur le bouton « Modifier » de la ligne du tableau. L'utilisateur au clavier doit deviner combien de tabulations le mèneront dans le formulaire, et une tabulation de trop l'envoie dans le tableau caché derrière le voile — où il peut atteindre et actionner un bouton « Supprimer » qu'il ne voit pas. Un lecteur d'écran n'annonce ni l'ouverture d'un dialogue ni son titre. Échap ne ferme pas : la seule sortie est le bouton « Annuler ». C'est la règle « tout formulaire est utilisable au clavier » qui tombe.

**Correction proposée :** deux options. Soit s'appuyer sur l'élément natif `<dialog>` avec `showModal()`, qui apporte gratuitement le piège de focus, Échap et l'inertisation du fond. Soit, puisque `@radix-ui/react-slot` est déjà une dépendance, ajouter `@radix-ui/react-dialog` — même famille, comportement conforme aux pratiques WAI-ARIA. À arbitrer par l'architecte : la seconde option ajoute une dépendance.

**Effort :** M

### [MAJEUR] Le plan de table n'a pas d'alternative clavier exploitable, et dnd-kit annonce en anglais

**Où :** `apps/web/src/components/TableBoard.tsx:63` · `apps/web/src/components/HouseholdChip.tsx:5-17`

**Constat :** `DndContext` est monté sans prop `sensors`, sans `accessibility` et sans `screenReaderInstructions`. Les valeurs par défaut de dnd-kit rendent le déplacement au clavier techniquement possible, mais inutilisable en pratique et non localisé.

**Preuve :**

```tsx
// TableBoard.tsx:63 — aucune configuration
<DndContext onDragEnd={handleDragEnd}>
```

```tsx
// HouseholdChip.tsx:5 — attributs par défaut uniquement
const { attributes, listeners, setNodeRef, transform } = useDraggable({ id: household.id });
```

Trois conséquences, dans l'ordre de gravité :

1. `KeyboardSensor` déplace l'élément par pas de 25 px et repose sur la détection de collision. Or les zones sont disposées en `grid md:grid-cols-3` (`TableBoard.tsx:64`) : atteindre au clavier une table située à l'autre bout d'une grille de plusieurs rangées demande des dizaines d'appuis sur les flèches, sans repère visuel de la cible atteinte autre que la bordure de `DroppableZone` (`TableBoard.tsx:18`).
2. Les annonces par défaut de dnd-kit destinées au lecteur d'écran sont en anglais, tout comme l'`aria-roledescription` posé par `attributes`. Aucune n'est surchargée.
3. Il n'existe **aucun** chemin non-glisser : la page ne propose ni menu « Assigner à… » par foyer, ni bouton de retrait. Un utilisateur qui n'utilise pas la souris, ou qui est sur un écran tactile étroit, n'a pas de solution de repli.

À noter, `TableBoard.test.tsx` teste `dragEndTarget` en isolation — un choix judicieux et assumé, documenté lignes 36-38 — mais aucun test ne couvre l'interaction clavier.

**Impact :** le plan de table est une fonction admin, donc l'audience est petite, ce qui justifie MAJEUR plutôt que BLOQUANT. Il n'en reste pas moins qu'elle est inaccessible sans souris, et que les annonces anglaises contredisent la règle de langue.

**Correction proposée :** ajouter à chaque `HouseholdChip` un `<select>` « Table » listant les tables plus « Non assigné », qui déclenche les mêmes `onAssign`/`onUnassign`. C'est l'alternative la plus robuste et elle sert aussi le tactile. En complément, fournir `announcements` et `screenReaderInstructions` en français à `DndContext`. Confirmer au préalable la signature exacte de l'API `accessibility` de dnd-kit 6.3 via context7 — je ne l'ai pas exercée ici.

### [MAJEUR] Aucune confirmation avant la suppression d'un foyer ou d'une table

**Où :** `apps/web/src/pages/admin/HouseholdsPage.tsx:100-102` · `apps/web/src/pages/admin/TablesPage.tsx:167-169`

**Constat :** les deux boutons « Supprimer » déclenchent la mutation directement au clic, sans étape intermédiaire, sans possibilité d'annulation et sans état de chargement.

**Preuve :**

```tsx
// HouseholdsPage.tsx:100
<Button variant="destructive" size="sm" onClick={() => deleteMutation.mutate(h.id)}>
  Supprimer
</Button>
```

```tsx
// TablesPage.tsx:167
<Button size="sm" variant="destructive" onClick={() => deleteTable.mutate(table.id)}>
  Supprimer
</Button>
```

Côté serveur, `households.service.ts:57-61` supprime sans détour : `await this.prisma.household.delete({ where: { id } })`.

**Impact :** dans le tableau des foyers, le bouton « Supprimer » est directement adjacent au bouton « Modifier » (`HouseholdsPage.tsx:97-102`), sur des lignes serrées, avec une cible tactile de taille `sm`. Un clic manqué détruit définitivement un foyer et, avec lui, son `linkId` — c'est-à-dire le lien déjà envoyé à cette famille, qui renverra désormais une 404. La réponse de l'invité est perdue avec. ### [PISTE] L'expiration du cookie en cours de session provoque un rechargement complet, sans avertissement

**Où :** `apps/web/src/lib/api.ts:16-34` · `apps/web/src/auth/AuthContext.tsx:14-24` · `apps/web/src/auth/ProtectedRoute.tsx:4-9`

**Constat :** le mécanisme est correct sur le fond et bien documenté (`api.ts:5-15`) : un 401 hors `/auth/*` déclenche `window.location.href = "/login"`, ce qui purge à la fois l'état d'authentification et tout le cache React Query. `ProtectedRoute` couvre bien le premier rendu, et l'exclusion de `/auth/*` protège correctement la page invité, qui déclenche pourtant un `/auth/me` en 401 à chaque chargement puisque `AuthProvider` enveloppe l'application entière.

1. La navigation dure abandonne sans prévenir toute saisie en cours. ## Ce qui est bien fait

**Les types partagés sont respectés sans exception.** Aucun `any` dans `apps/web/src`, aucune interface serveur redéclarée localement, aucune duplication de `RsvpStatus` ou des DTO. `HouseholdFormValues` (`HouseholdFormDialog.tsx:12-15`) étend `CreateHouseholdDto` au lieu de le recopier, et le commentaire explique pourquoi une seule valeur doit satisfaire les deux DTO. C'est la partie du code à laquelle il ne faut pas toucher.

**Les labels de formulaire sont réellement associés, partout.** Chaque champ de `RsvpForm`, `HouseholdFormDialog`, `LoginPage` et `TablesPage` a un `htmlFor` pointant vers un `id` existant ; `SettingsPage` utilise `useId()` pour les champs générés (`SettingsPage.tsx:97`, `:131`), et les champs d'édition en ligne de `TablesPage`, qui ne pouvaient pas porter de label visible, ont un `aria-label` contextualisé — `aria-label={\`Capacité de ${table.name}\`}` (`TablesPage.tsx:132`) distingue correctement des champs autrement identiques. Ce point de la grille est réglé, il n'y a rien à y reprendre.

**Les commentaires documentent les bugs corrigés, pas le code évident.** `api.ts:5-15`, `TableBoard.tsx:29-39`, `RsvpForm.tsx:18-20`, `InvitationPage.tsx:27-29` et `HouseholdFormDialog.tsx:46-49` expliquent chacun une décision non évidente et le défaut qu'elle prévient. C'est ce qui a permis à cet audit de distinguer les choix délibérés des oublis, et c'est une pratique à préserver — le constat BLOQUANT ci-dessus a été trouvé précisément en vérifiant si le commentaire de `HouseholdFormDialog.tsx:46-49` tenait toutes ses promesses.

**Le garde-fou d'authentification tient même API éteinte — vérifié.** Une navigation directe vers `http://localhost:5173/admin/settings` sans session, API injoignable, rend le formulaire de connexion et rien d'autre ; le texte intégral de la page est « Connexion organisateurs / Email / Mot de passe / Se connecter / Se connecter avec Google ». Le `.catch(() => setAdmin(null))` de `AuthContext.tsx:22` dégrade correctement l'échec réseau en « non authentifié », et `AdminLayout` est bien imbriqué *dans* `ProtectedRoute` (`App.tsx:16-24`), donc ni la navigation admin ni le bouton de déconnexion ne fuitent vers un visiteur non connecté. **Le statut RSVP n'est jamais porté par la seule couleur.** `StatusBadge` (`StatusBadge.tsx:16-22`) associe systématiquement un fond coloré à un libellé français explicite, et le dépassement de capacité de `TableBoard.tsx:80-83` double le rouge d'un « ⚠ dépassement » textuel. Rien à corriger sur ce point de la grille non plus.
