## Synthèse

Les suites unitaires tournent proprement (101 tests, 0 échec) et sont dans l'ensemble de bonne facture : assertions sur les codes de statut/exceptions plutôt que sur des messages, mocks minimaux plutôt que des simulateurs de service complet, aucun `.skip`/`.only` trouvé, aucun fichier de test sans `expect`. Six des huit invariants métier sont couverts par un test qui échouerait si on retirait la protection. Le point le plus grave de cet audit n'est pas un test manquant mais une protection manquante : `HouseholdsService.update` revalide `confirmedCount <= allocatedSeats` mais ne revérifie jamais la capacité de la table quand on augmente les places d'un foyer déjà assis — aucun test ne peut donc « couvrir » cet invariant puisqu'il n'existe rien à couvrir. La suite e2e, qui porte la seule preuve bout-en-bout du garde admin, ne peut pas tourner dans cet environnement faute de base de données : la protection admin est correctement écrite sur le papier mais non vérifiée ici.

## Constats

### [BLOQUANT] `PATCH /admin/households/:id` peut faire dépasser la capacité d'une table déjà assise, sans aucune vérification

**Où :** `apps/api/src/households/households.service.ts:38-55`

**Constat :** `HouseholdsService.update` revalide uniquement `confirmedCount <= allocatedSeats` (ligne 48). Il ne lit jamais `household.tableId`, ne consulte jamais la capacité de la table, et n'appelle aucune méthode équivalente à `TablesService.assignHousehold`. Un admin qui augmente `allocatedSeats` (ou `confirmedCount`) d'un foyer déjà assis à une table peut donc faire dépasser la capacité de cette table sans que l'API ne le refuse — alors que le même dépassement est bloqué en `409` sur `PATCH /admin/tables/:id/assign/:householdId` (`tables.service.ts:92-96`) et sur `PATCH /admin/tables/:id` en réduction de capacité (`tables.service.ts:43-50`). Deux routes qui affectent la même donnée (occupation d'une table) n'appliquent pas la même règle.

**Preuve :**
```ts
// apps/api/src/households/households.service.ts:38-55
async update(id: string, dto: UpdateHouseholdDto) {
  const household = await this.findOne(id);
  const allocatedSeats = dto.allocatedSeats ?? household.allocatedSeats;
  const confirmedCount = dto.confirmedCount ?? household.confirmedCount;
  if (confirmedCount !== null && confirmedCount > allocatedSeats) {
    throw new BadRequestException('confirmedCount cannot exceed allocatedSeats');
  }
  // aucune lecture de household.tableId, aucune requête sur Table ici
  return this.prisma.household.update({ where: { id }, data: dto });
}
```
`apps/api/src/households/households.service.spec.ts` ne contient aucun cas avec `tableId` renseigné : `grep -n "tableId" apps/api/src/households/households.service.spec.ts` ne retourne rien. Il n'existe donc pas de protection à couvrir par un test — le trou est dans le code, pas seulement dans la suite.

**Impact :** un foyer déjà assis (10 places prises sur une table de 10) peut voir son `allocatedSeats` monté à 15 via l'admin sans jamais toucher `TablesService`. Le plan de table affiché aux invités (`InvitationService.getInvitation` → `seatingPlan.neighbors`) devient incohérent avec la capacité réelle de la salle — corruption silencieuse de l'invariant 4, un des cas explicitement cités par le backend comme point d'attention.

**Correction proposée :** dans `HouseholdsService.update`, quand `household.tableId` est renseigné et que `allocatedSeats` ou `confirmedCount` augmente, recalculer l'occupation de la table (même logique que `TablesService.seatsTaken`) et lever `ConflictException` en cas de dépassement — ou déléguer ce calcul à `TablesService` pour éviter la duplication de règle entre les deux services.

**Effort :** M

### [MAJEUR] Course sur la capacité de table dans `assignHousehold` — lecture puis écriture hors transaction

**Où :** `apps/api/src/tables/tables.service.ts:75-102`

**Constat :** `assignHousehold` lit l'occupation de la table (`findUnique` + `households`) puis, après un calcul en mémoire, écrit `household.update({ data: { tableId } })` — deux requêtes Prisma séparées, sans `$transaction` ni verrou. Deux appels concurrents à `assignHousehold` sur la même table (deux organisateurs qui glissent-déposent deux foyers différents en même temps sur une table presque pleine) peuvent tous les deux lire la même occupation `occupied` avant que l'un des deux n'écrive, et tous les deux passer le test `occupied + incoming > table.capacity` alors qu'ensemble ils dépassent la capacité.

**Preuve :**
```ts
// apps/api/src/tables/tables.service.ts:75-96
async assignHousehold(tableId: string, householdId: string) {
  const table = await this.prisma.table.findUnique({ where: { id: tableId }, include: { households: true } });
  // ... lecture ...
  const occupied = this.seatsTaken(table.households.filter((h) => h.id !== householdId));
  const incoming = household.confirmedCount ?? household.allocatedSeats;
  if (occupied + incoming > table.capacity) { throw new ConflictException(...); }
  return this.prisma.household.update({ where: { id: householdId }, data: { tableId } }); // écriture séparée
}
```

**Impact :** dépassement possible de la capacité physique d'une table lors d'assignations concurrentes — improbable en usage normal (un seul admin à la fois côté V1) mais réel si deux organisateurs travaillent en parallèle le jour J. Aucun test, unitaire ou e2e, n'exerce ce scénario : les mocks Jest de `tables.service.spec.ts` n'émulent pas de concurrence, et le seul test capable de la révéler (deux requêtes HTTP simultanées contre une vraie base) n'existe pas dans `apps/api/test/`.

**Correction proposée :** englober lecture et écriture dans `this.prisma.$transaction(...)`, ou ajouter une contrainte applicative type update conditionnel (`updateMany` avec `where` incluant un contrôle d'occupation recalculé côté SQL). Écrire ensuite un test d'intégration qui déclenche deux `assignHousehold` en parallèle contre une base réelle pour prouver la correction.

**Effort :** M

### [MAJEUR] La suite e2e ne tourne pas dans cet environnement — seule preuve bout-en-bout du garde admin non vérifiée

**Où :** `apps/api/test/admin-auth.e2e-spec.ts`, `apps/api/test/auth.e2e-spec.ts`

**Constat :** `admin-auth.e2e-spec.ts` est le seul test qui vérifie, sur une application NestJS réellement montée, que les 13 routes `/admin/*` (lecture et écriture) renvoient `401` sans cookie, et qu'un JWT signé avec un autre secret est rejeté. C'est un bon test : boucle systématique sur toutes les routes, assertion sur le code de statut. Mais il exige `DATABASE_URL`/`JWT_SECRET` pour monter `AppModule`, absents dans cet environnement — voir sortie brute plus haut. Résultat : la garantie « aucune route admin non protégée » n'a **aucune preuve d'exécution** ici, seulement une preuve de bonne écriture sur le papier.

**Preuve :** sortie de `pnpm --filter @invitation-app/api test:e2e` collée ci-dessus — `Config validation error: "DATABASE_URL" is required. "JWT_SECRET" is required`, 3 suites échouées, 18 tests échoués avant même d'atteindre une assertion.

**Impact :** un développeur qui retire `@UseGuards(JwtAuthGuard)` d'un contrôleur admin ne serait détecté par aucune suite exécutable dans cet environnement (CI incluse, si elle est configurée de façon identique sans base de données de test).

**Correction proposée :** ce n'est pas un défaut du test lui-même mais un défaut d'environnement de vérification — hors du périmètre lecture seule de cet audit. À signaler à l'équipe DevOps/CI : la CI doit provisionner une base de test (`DATABASE_URL`) et un `JWT_SECRET` factice pour que `test:e2e` s'exécute réellement, sinon ce filet de sécurité est un théâtre de tests.

**Effort :** S (config CI) — hors périmètre de cet audit.

### [MINEUR] Cas limite manquant : assignation pile à la capacité exacte de la table

**Où :** `apps/api/src/tables/tables.service.spec.ts:6-86` (`describe('TablesService.assignHousehold', ...)`)

**Constat :** le code utilise une comparaison stricte `occupied + incoming > table.capacity` (`tables.service.ts:92`), ce qui autorise correctement une table à se remplir pile à sa capacité. Ce comportement est testé pour `update` (réduction de capacité, `tables.service.spec.ts:131-144` : « allows shrinking capacity down to exactly the seats taken ») mais **pas pour `assignHousehold`** : le test « assigns the household when capacity allows it » (lignes 49-68) laisse 3 places libres sur 10, jamais pile 0. Un `>` accidentellement changé en `>=` casserait le remplissage exact d'une table sans qu'aucun test ne le détecte du côté assignation.

**Impact :** faible — le comportement actuel est correct, seule la protection contre une régression manque, et côté assignation c'est le chemin le plus fréquemment exercé en usage réel (remplir une table jusqu'au bout).

**Correction proposée :** ajouter un cas où `occupied + incoming === table.capacity` et vérifier `resolves.not.toThrow()`.

**Effort :** S

## Ce qui est bien fait

- **Discipline sur les assertions :** systématiquement des codes de statut/types d'exception (`toThrow(ConflictException)`, `.expect(401)`, `.expect(409)` implicite via `ConflictException`) plutôt que des messages — exactement ce que demande le protocole d'audit. Aucune occurrence trouvée d'un test qui échouerait uniquement sur un changement de texte d'erreur côté API.
- **Tests de régression nommés et documentés :** `households.service.spec.ts:106-117` (rejette une réduction d'`allocatedSeats` sous le `confirmedCount` existant), `HouseholdFormDialog.test.tsx:69-91` (ne jamais écraser un `confirmedCount: null` par `0`), `dashboard.service.spec.ts:39-53` (exclut les chaînes vides historiques des notes diététiques) — chacun porte un commentaire expliquant le bug réel qu'il empêche de revenir, pas juste ce que fait le code.
- **Mocks Prisma minimaux et localisés :** chaque suite ne mocke que les méthodes Prisma réellement appelées par le service testé (`{ table: { findUnique }, household: { findUnique, update } }`), jamais un faux service complet qui masquerait un chemin de code non exercé.
