## Synthèse

Le socle de sécurité est sain : les quatre contrôleurs `/admin/*` portent bien `@UseGuards(JwtAuthGuard)` au niveau classe, il n'existe aucune route admin non protégée, aucun secret en dur, et `linkId` ne fuite dans aucune réponse d'API — le calcul des voisins de table projette explicitement `displayName` et `confirmedCount`, rien d'autre. Le problème numéro un n'est pas dans la logique métier mais dans l'outillage : **`build`, `test` et `lint` échouent tous les trois sur ce checkout**, parce que rien ne déclenche `prisma generate` en dehors du Dockerfile. Le filet de tests écrit pour garder les invariants (commits `a5d1fbc`, `513550b`) est donc actuellement du code mort, et c'est ce qu'il faut réparer en premier. Sur le métier, les 8 invariants sont tous implémentés en service et non seulement en DTO, mais trois trous réels subsistent : la vérification de capacité de table est un TOCTOU hors transaction, `HouseholdsService.update` laisse un admin gonfler `allocatedSeats` d'un foyer déjà assis sans revérifier sa table, et il ne remet pas `confirmedCount` à 0 quand il passe un foyer à `DECLINED` — ce qui fausse à la fois le dashboard et l'occupation des tables. Enfin, tous les messages d'erreur de l'API publique sont en anglais et sont affichés verbatim à l'invité : le défaut connu du projet n'a été corrigé que côté front.

### [MAJEUR] Capacité de table : lecture et écriture hors transaction, deux assignations concurrentes dépassent la capacité

**Où :** `apps/api/src/tables/tables.service.ts:75-102` (`assignHousehold`), même défaut en `36-52` (`update`)

**Constat :** `assignHousehold` fait quatre aller-retours indépendants vers la base : lecture de la table avec ses foyers (l.76-79), lecture du foyer entrant (l.82-84), calcul de l'occupation en mémoire (l.87-90), comparaison (l.92), puis écriture (l.98-101). Aucun `this.prisma.$transaction`, aucun verrou de ligne, aucune contrainte SQL équivalente dans `migration.sql`. La fenêtre entre la lecture et l'écriture n'est protégée par rien.

**Preuve :**

```ts
const table = await this.prisma.table.findUnique({   // l.76 — LECTURE
  where: { id: tableId },
  include: { households: true },
});
// ...
const occupied = this.seatsTaken(                     // l.87 — calcul en mémoire
  table.households.filter((h) => h.id !== householdId),
);
const incoming = household.confirmedCount ?? household.allocatedSeats;

if (occupied + incoming > table.capacity) {           // l.92 — VÉRIFICATION
  throw new ConflictException(/* ... */);
}

return this.prisma.household.update({                 // l.98 — ÉCRITURE
  where: { id: householdId },
  data: { tableId },
});
```

Scénario exact de dépassement, sur la table `T` de capacité 10 occupée par le foyer `A` (6 places) :

1. L'organisatrice, sur son téléphone, fait glisser le foyer `B` (3 places) sur `T`. Requête 1 lit `T` : `occupied = 6`.
2. L'organisateur, sur son portable, fait glisser le foyer `C` (3 places) sur `T` au même instant. Requête 2 lit `T` **avant que la requête 1 n'ait commité son UPDATE** : elle lit elle aussi `occupied = 6`.
3. Requête 1 : `6 + 3 = 9 <= 10` → écrit `B.tableId = T`.
4. Requête 2 : `6 + 3 = 9 <= 10` → écrit `C.tableId = T`.
5. État final : `T` porte `A + B + C = 12` convives pour 10 places. Aucun `409` n'a été renvoyé, personne n'est prévenu.

L'isolation PostgreSQL par défaut (READ COMMITTED) ne suffit pas : même enveloppé dans un `$transaction` naïf, chaque transaction lirait un instantané validé antérieur à l'écriture concurrente. Il faut un verrou explicite ou une isolation sérialisable.

**Impact :** invariant n°4 (« la capacité de table est vérifiée serveur ») violé silencieusement. L'app expose un tableau de placement en glisser-déposer (commit `70ea34e`) et le couple travaille dessus à deux — deux clics simultanés ne sont pas un scénario exotique ici. La table sur-remplie n'est jamais détectée après coup : `findAll` la renvoie telle quelle, et `update` (l.43-50) n'est le seul endroit qui recompte que si l'admin touche au champ `capacity`. L'erreur se découvre le jour du mariage.

**Correction proposée :** envelopper `assignHousehold` dans un `$transaction` et verrouiller la ligne de table avant de compter, via un `SELECT ... FOR UPDATE` (`$queryRaw`) sur `Table` — ou passer la transaction en `Serializable` avec une politique de retry sur erreur de sérialisation. Appliquer le même traitement à `update` quand `capacity` change. Un test d'intégration lançant deux `assignHousehold` en `Promise.all` sur une base réelle est le seul moyen de prouver la correction ; il ne pourra pas être écrit tant que BLOQUANT-1 n'est pas levé.

**Effort :** M

*Note sur la sévérité : classé MAJEUR et non BLOQUANT parce qu'un `curl` isolé se heurte toujours correctement au `409`. Ce n'est pas un contournement délibéré, c'est une fenêtre de concurrence — ce que la grille range explicitement en MAJEUR.*

### [MAJEUR] `PATCH /admin/households/:id` permet d'augmenter `allocatedSeats` d'un foyer déjà assis sans revérifier la capacité de sa table

**Où :** `apps/api/src/households/households.service.ts:38-55`

**Constat :** `HouseholdsService.update` ne valide qu'une chose : `confirmedCount <= allocatedSeats` (l.46-52). Il ne lit jamais `household.tableId` et n'interroge jamais la table correspondante. Or `TablesService.seatsTaken` (`tables.service.ts:60-67`) calcule l'occupation d'une table comme la somme de `confirmedCount ?? allocatedSeats` de ses foyers. Augmenter l'un de ces deux champs augmente donc mécaniquement l'occupation de la table où le foyer est assis, sans qu'aucun contrôle ne se déclenche.

**Preuve :**

```ts
const allocatedSeats = dto.allocatedSeats ?? household.allocatedSeats;
const confirmedCount = dto.confirmedCount ?? household.confirmedCount;
if (confirmedCount !== null && confirmedCount > allocatedSeats) {
  throw new BadRequestException(
    'confirmedCount cannot exceed allocatedSeats',
  );
}

return this.prisma.household.update({ where: { id }, data: dto });  // l.54
```

Scénario, avec une seule requête, sans aucune concurrence :

1. Table `T`, capacité 10. Foyer `A` (6 places) et foyer `B` (`allocatedSeats: 4`, `status: PENDING`, `confirmedCount: null`) y sont assis. `seatsTaken` = 6 + 4 = 10. La table est pleine, `assignHousehold` refuserait tout ajout par `409`.
2. `curl -X PATCH /admin/households/B -d '{"allocatedSeats": 9}'` — cookie admin valide.
3. `update` compare `confirmedCount (null)` : la condition `confirmedCount !== null` est fausse, aucune exception. Écriture.
4. `seatsTaken(T)` vaut désormais 6 + 9 = **15 pour une table de 10 places**, produite par un chemin que le serveur a explicitement autorisé.

Le même code a pourtant été durci dans l'autre sens : `tables.service.ts:39-42` porte le commentaire « *update must not be a back door into the same broken state* » et interdit de rétrécir `capacity` sous l'occupation. La porte dérobée symétrique, côté foyer, est restée ouverte.

**Impact :** invariant n°4 contournable par une seule requête HTTP délibérée, sans course. L'acteur est un admin authentifié (d'où MAJEUR et non BLOQUANT), mais le geste n'a rien de malveillant : « finalement ils viennent à 9 » est exactement ce qu'un organisateur tape à trois semaines du mariage. Le plan de table devient faux et rien ne le signale. À noter que le chemin public est sain par construction : `submitRsvp` plafonne `confirmedCount` à `allocatedSeats`, il ne peut donc que faire baisser l'occupation.

**Correction proposée :** dans `HouseholdsService.update`, si le foyer a un `tableId` et que `allocatedSeats` ou `confirmedCount` augmentent, recalculer l'occupation de la table cible et lever un `409 ConflictException` en cas de dépassement — en réutilisant la logique de `TablesService.seatsTaken` plutôt qu'en la dupliquant (l'extraire dans un helper partagé, ou faire dépendre `HouseholdsModule` de `TablesService`). Décider avec l'architecte du comportement attendu : refus sec, ou désassignation automatique du foyer.

**Effort :** M

### [MAJEUR] Un `DECLINED` saisi par l'admin laisse `confirmedCount` intact : convives fantômes au dashboard et places fantômes à table

**Où :** `apps/api/src/households/households.service.ts:38-55` — à comparer à `apps/api/src/invitation/invitation.service.ts:79`

**Constat :** le chemin public normalise explicitement `confirmedCount` à `0` quand le foyer décline. Le chemin admin, lui, écrit le DTO brut : si l'admin envoie `{"status": "DECLINED"}` seul, `confirmedCount` n'est pas dans le `data`, Prisma ne touche donc pas la colonne et l'ancienne valeur reste en base. Les deux chemins produisent des états différents pour le même fait métier.

**Preuve :**

```ts
// invitation.service.ts:75-84 — chemin public, correct
return this.prisma.household.update({
  where: { id: linkId },
  data: {
    status: dto.status,
    confirmedCount: dto.status === 'DECLINED' ? 0 : dto.confirmedCount,
    // ...
  },
});
```

```ts
// households.service.ts:54 — chemin admin, aucune normalisation
return this.prisma.household.update({ where: { id }, data: dto });
```

Scénario :

1. Le foyer `Famille Dupont` (`allocatedSeats: 4`) confirme 4 personnes via son lien. En base : `status: CONFIRMED`, `confirmedCount: 4`. Il est assis à la table `T`.
2. Ils téléphonent au couple : finalement ils ne viennent pas. L'organisateur ouvre la fiche et bascule le statut — invariant n°2, les routes admin ne sont jamais bloquées par la date, c'est le geste prévu.
3. `PATCH /admin/households/xxxx` avec `{"status": "DECLINED"}`. Aucune validation ne s'y oppose.
4. En base : `status: DECLINED`, **`confirmedCount: 4`**.
5. `dashboard.service.ts:18-20` fait `aggregate({ _sum: { confirmedCount: true } })` **sans clause `where`** : les 4 convives fantômes sont comptés dans `totalConfirmedGuests`. Le couple commande 4 repas de trop.
6. `tables.service.ts:64` fait `confirmedCount ?? allocatedSeats` : la table `T` reste facturée 4 places pour un foyer absent, et refusera par `409` un foyer qui aurait pu s'y asseoir.

Cas symétrique, sur le piège que le commit `4f5574f` a déjà corrigé côté web : `PATCH {"status": "PENDING"}` sur un foyer confirmé laisse `confirmedCount: 4`, ce qui détruit la distinction « pas encore répondu » (`null`) / « a répondu ». Le service n'a aucun moyen de remettre `confirmedCount` à `null` : `UpdateHouseholdDto.confirmedCount` est un `number` optionnel, `null` n'est pas représentable.

**Impact :** corruption de données produite par le geste admin le plus banal du projet, invisible jusqu'à ce qu'on compte les assiettes. Touche le chiffre le plus regardé du dashboard (`totalConfirmedGuests`) et l'occupation réelle des tables.

**Correction proposée :** dans `HouseholdsService.update`, dériver `confirmedCount` du `status` résultant comme le fait `submitRsvp` : `0` si le statut devient `DECLINED`, `null` s'il redevient `PENDING` (ce qui suppose d'autoriser `null` dans le DTO, par exemple via `@IsOptional()` + `@ValidateIf`), et laisser la valeur fournie sinon. Ajouter en défense un `where: { status: 'CONFIRMED' }` sur l'agrégat de `dashboard.service.ts:18-20`, pour que les lignes déjà corrompues en base cessent d'être comptées. Attention à ne pas réintroduire le bug de `4f5574f` en écrivant `0` là où il faut `null`.

**Effort :** M

### [MINEUR] Aucun filtre d'exception Prisma : plusieurs chemins renvoient 500 là où 404 est attendu, dont un sur la route publique

**Où :** `apps/api/src/tables/tables.service.ts:104-108` · `apps/api/src/settings/settings.service.ts:9-13` · `apps/api/src/invitation/invitation.service.ts:20, 55` · aucun `*.filter.ts` dans `apps/api/src/**`

**Constat :** il n'existe aucun `ExceptionFilter` dans le projet, donc les erreurs Prisma remontent brutes et Nest les transforme en `500 Internal Server Error`. Trois chemins y tombent :

**Preuve :**

```ts
// tables.service.ts:104-108 — aucune vérification d'existence, contrairement à
// households.service.ts:57-61 qui appelle findOne() avant de supprimer
unassignHousehold(householdId: string) {
  return this.prisma.household.update({
    where: { id: householdId },
    data: { tableId: null },
  });
}
```

`PATCH /admin/tables/unassign/id-inconnu` déclenche un `P2025` Prisma → **500** au lieu de **404**. `TablesService.remove` et `HouseholdsService.remove` font correctement le `findOne` préalable ; celui-ci a été oublié.

```ts
// settings.service.ts:9-13 et invitation.service.ts:20, 55
this.prisma.weddingSettings.findUniqueOrThrow({ where: { id: 'singleton' } });
```

Sur une base migrée mais non seedée (le seed n'est appelé nulle part au démarrage — `Dockerfile:34` ne lance que `prisma migrate deploy`), `findUniqueOrThrow` lève `P2025`. Cela produit un **500 sur la route publique `GET /invitation/:linkId`** : le tout premier invité qui ouvre son lien après un déploiement sur base neuve reçoit une erreur serveur brute.

**Impact :** codes de statut faux pour le front admin, qui ne peut pas distinguer « ressource inexistante » de « serveur en panne ». Et sur la route publique, un 500 non maîtrisé à l'endroit exact où l'expérience invité commence.

**Correction proposée :** ajouter un `PrismaClientExceptionFilter` global mappant au minimum `P2025` → 404 et `P2002` → 409, et ajouter le contrôle d'existence manquant dans `unassignHousehold` pour rester cohérent avec les autres services. Traiter séparément la question du seed : `WeddingSettings` doit exister avant le premier trafic.

**Effort :** S

### [MINEUR] La réponse publique est construite sans `select` et livre plus de colonnes que le contrat déclaré

**Où :** `apps/api/src/invitation/invitation.service.ts:14-47` · contrat : `packages/shared/src/index.ts:3-12` et `20-28`

**Constat :** `getInvitation` renvoie les objets Prisma entiers (`return { household, wedding, seatingPlan }`, l.46) après un `findUnique` sans `select`. Le contrat partagé décrit pourtant des projections plus étroites.

### [MINEUR] Codes de statut HTTP : 401 au lieu du 403 spécifié pour la whitelist Google, et 201 sur login/logout

**Où :** `apps/api/src/auth/strategies/google.strategy.ts:37-41` · `apps/api/src/auth/auth.controller.ts:53-68`

**Constat :** deux écarts entre les codes émis et ceux attendus.

**Preuve :**

```ts
// google.strategy.ts:37-41
const email = profile.emails?.[0]?.value;
const user = await this.authService.validateGoogleUser(email, profile.id);
if (!user)
  return done(new UnauthorizedException('Email not authorized'), false);
```

La règle du domaine est explicite : « Google : l'email doit figurer dans `ALLOWED_ADMIN_EMAILS`, sinon **403** sans création de compte ». Le code renvoie **401**. La partie importante de la règle est respectée — `auth.service.ts:35` sort avant tout `create`, et `auth.service.google.spec.ts:149-156` l'atteste — mais le code de statut contredit la spec.

Par ailleurs, `@Post('login')` et `@Post('logout')` (`auth.controller.ts:54` et `64`) héritent du **201 Created** par défaut de Nest sur les `POST` ; le test e2e existant l'entérine (`test/auth.e2e-spec.ts:107` : `.expect(201)`). Une authentification ne crée aucune ressource.

**Impact :** faible. Le 401 sur Google reste correct fonctionnellement (l'accès est refusé, aucun compte n'est créé) mais oblige le front à traiter deux causes distinctes — session absente / email non autorisé — sous le même code, alors que le `401` déclenche justement une redirection automatique vers `/login` côté web (`apps/web/src/lib/api.ts:16-19`). Les 201 sont un désalignement de contrat sans conséquence utilisateur.

**Correction proposée :** remplacer `UnauthorizedException` par `ForbiddenException` dans `google.strategy.ts` et franciser le message. Ajouter `@HttpCode(200)` sur `login` et `logout`, en mettant à jour `test/auth.e2e-spec.ts`. Si l'écart 401/403 est un choix assumé, il doit être arbitré et la spec corrigée en conséquence — pas laissé en contradiction silencieuse.

## Ce qui est bien fait

**Les gardes admin sont complètes — vérifiées contrôleur par contrôleur, aucun trou.** Les quatre contrôleurs sous `/admin/*` portent `@UseGuards(JwtAuthGuard)` au niveau classe, ce qui couvre les 13 routes sans exception : `households.controller.ts:16` (5 routes), `tables.controller.ts:16` (6 routes), `settings.controller.ts:6` (2 routes), `dashboard.controller.ts:5` (1 route). `invitation.controller.ts` est le seul contrôleur non gardé et il porte un commentaire qui l'assume explicitement (l.5-6), conformément à l'invariant n°1. `health.controller.ts` ne renvoie que `{ status: 'ok' }`. Aucun secret de repli nulle part : `auth.module.ts:22` et `jwt.strategy.ts:21` utilisent `getOrThrow`, tous deux commentés pour expliquer pourquoi il ne faut pas y toucher. `test/admin-auth.e2e-spec.ts` énumère les 13 routes et attend 401 — je n'ai pas pu l'exécuter (voir BLOQUANT-1), mais c'est le bon test, écrit au bon endroit. Ne rien toucher ici.

**`linkId` ne fuite nulle part.** C'était le point de contrôle le plus important après les gardes, et il est propre. Le calcul des voisins de table dans `invitation.service.ts:36-41` projette explicitement `displayName` et `confirmedCount`, jamais `h.id` — un invité ne peut donc pas récupérer le lien d'accès de ses voisins de table, et `invitation.service.spec.ts:95-105` verrouille exactement ce comportement. Le `linkId` n'apparaît par ailleurs dans aucun log applicatif : `grep -rn "console\.\|Logger" apps/api/src` ne renvoie rien du tout. Les routes admin qui renvoient `id` sont légitimes, l'organisateur en a besoin pour composer les liens.

**Les invariants sont dans les services, pas dans les DTO.** Un `curl` direct se heurte bien au serveur sur l'essentiel : la deadline RSVP (`invitation.service.ts:58-60`, `403`, et strictement rien d'équivalent sur les routes admin — invariant n°2 correctement asymétrique), le plafond `confirmedCount <= allocatedSeats` sur les deux chemins (`invitation.service.ts:68-72` et `households.service.ts:46-52`), la capacité de table (`tables.service.ts:92`, `409`, plus la porte dérobée de `update` déjà fermée l.43-50), et le plan de table qui renvoie `seatingPlan: null` côté serveur plutôt que de laisser le front masquer les données (`invitation.service.ts:24-44`, invariant n°6). Les commentaires laissés par les correctifs précédents (`a5d1fbc`, `513550b`) expliquent le *pourquoi* de chaque garde-fou plutôt que le *quoi* : c'est ce qui a rendu cet audit rapide, et c'est à préserver.

Le schéma respecte le modèle du domaine, `confirmedCount` est bien `Int?` nullable (`schema.prisma:21`) et la migration versionnée `20260819145910_init` est cohérente avec lui — aucune trace de `db push`.
