## Constats

### [MAJEUR] Aucun `packageManager` épinglé : la version de pnpm — et donc le Node minimum requis — n'est pas reproductible

**Où :** `package.json:1-13` (racine) · `apps/api/Dockerfile:1-9` (commentaire) · `apps/api/Dockerfile:10,27` (`FROM node:22-slim`)

**Constat :** `package.json` déclare `"engines": { "node": ">=20" }` mais ne porte aucun champ `"packageManager"`. Le Dockerfile explique lui-même pourquoi c'est un problème : `corepack enable` sans `packageManager` résout la **dernière version de pnpm publiée au moment du build**, et pnpm 11.x — vérifié : `pnpm --version` renvoie `11.22.0` dans cet environnement — exige Node ≥ 22 pour s'exécuter (confirmé par la documentation pnpm : le support de Node 18 à 21 a été supprimé en pnpm 11). Le commentaire du Dockerfile le dit en toutes lettres : « that pnpm binary itself requires Node >= 22.13 to run at all (it crashes with ERR_UNKNOWN_BUILTIN_MODULE on Node 20) ». `git show HEAD:package.json` confirme qu'aucun commit n'a jamais ajouté `packageManager` (seul `e188537` touche ce fichier).

**Preuve :**

```json
// package.json (HEAD, confirmé par git show HEAD:package.json)
{
  "engines": { "node": ">=20" }
}
```

```dockerfile
# apps/api/Dockerfile:3-9
# Base image is node:22-slim (not node:20-slim) because this repo has no
# "packageManager" field pinning a pnpm version, so `corepack enable` resolves
# and downloads whatever the latest pnpm release is at build time (currently
# pnpm 11.x) — and that pnpm binary itself requires Node >= 22.13 to run at
# all (it crashes with ERR_UNKNOWN_BUILTIN_MODULE on Node 20).
```

```
$ node --version   # v22.16.0
$ pnpm --version   # 11.22.0
$ corepack --version   # 0.32.0
```

**Impact :** `engines.node ">=20"` est trompeur — une machine ou une future CI satisfaisant exactement cette contrainte (Node 20) ne peut pas exécuter `pnpm install` du tout dès qu'un `corepack enable` résout une pnpm récente, ce qui contredit directement l'exigence de reproductibilité du projet. Le Dockerfile s'en sort seulement parce qu'il fixe `node:22-slim` en dur — mais rien n'empêche une prochaine version majeure de pnpm de relever encore la barre sans qu'aucun code ne change, puisqu'aucune version n'est réellement figée. J'ai personnellement observé qu'une simple commande `pnpm --version` fait apparaître puis disparaître un `packageManager` dans `package.json` (auto-pin de corepack) — preuve que le premier poste ou la première CI qui exécutera une commande pnpm sur ce dépôt peut committer, sans review, un pin correspondant à la version « du jour ».

**Correction proposée :** ajouter explicitement `"packageManager": "pnpm@<version exacte>+sha512-..."` dans le `package.json` racine (la même valeur que celle déjà résolue localement peut servir de point de départ), et relever `engines.node` à `>=22.13` pour que la contrainte documentée corresponde à la contrainte réelle.

**Effort :** S

### [MAJEUR] `apps/web` retombe silencieusement sur `localhost:3000` si `VITE_API_URL` est absent sur Vercel

**Où :** `apps/web/src/lib/api.ts:1` · `apps/web/vite.config.ts` (aucune vérification) · `apps/web/.env.example:1-4`

**Constat :** `const API_URL = import.meta.env.VITE_API_URL ?? "http://localhost:3000";` est la seule ligne qui détermine la cible de toutes les requêtes du front. Rien dans `vite.config.ts` ni ailleurs ne fait échouer le build si `VITE_API_URL` est absent au moment du `vite build` exécuté par Vercel — Vite se contente de laisser `import.meta.env.VITE_API_URL` à `undefined`, le fallback s'applique, et le build se termine avec un code de sortie 0.

**Preuve :**

```ts
// apps/web/src/lib/api.ts:1
const API_URL = import.meta.env.VITE_API_URL ?? "http://localhost:3000";
```

```ts
// apps/web/vite.config.ts — aucune étape de validation d'env, contrairement à
// apps/api/src/config/env.validation.ts côté API
export default defineConfig({
  plugins: [react(), tailwindcss()],
  resolve: { alias: { "@": path.resolve(__dirname, "./src") } },
  test: { /* ... */ },
});
```

**Impact :** contrairement à l'API (qui refuse de démarrer sans `FRONTEND_URL`/`JWT_SECRET`/etc.), le front n'a **aucun garde-fou équivalent**. Un projet Vercel mal configuré (variable oubliée, mal nommée, ou définie seulement sur un autre environnement Vercel que celui utilisé) produit un déploiement marqué comme réussi par Vercel, mais où **chaque appel API du navigateur part vers `http://localhost:3000`** — c'est-à-dire échoue pour 100 % des visiteurs, invités comme admin, sans qu'aucune alerte de build ne le signale. C'est exactement le principe que le projet applique côté API (« un serveur qui démarre à moitié configuré est pire qu'un serveur qui refuse de démarrer ») mais qui n'a pas été porté côté front.

**Correction proposée :** ajouter une vérification au tout début de `vite.config.ts` (ou un petit script `prebuild`) qui lève une erreur si `mode === 'production'` et que `process.env.VITE_API_URL` est vide, pour faire échouer le build Vercel plutôt que de livrer un site cassé silencieusement.

**Effort :** S

### [MAJEUR] Le conteneur de production tourne en `root` : aucune directive `USER` dans le Dockerfile

**Où :** `apps/api/Dockerfile:27-34` (étape `runtime`)

**Constat :** l'image `node:22-slim` fournit un utilisateur `node` non privilégié prêt à l'emploi, mais le Dockerfile ne contient aucune directive `USER` — vérifié par `grep -n "USER" apps/api/Dockerfile`, aucune correspondance. Le process `node apps/api/dist/src/main.js` final s'exécute donc en `root` dans le conteneur.

**Preuve :**

```dockerfile
# apps/api/Dockerfile:27-34 — étape runtime complète, aucun USER
FROM node:22-slim AS runtime
WORKDIR /app
RUN apt-get update -y && apt-get install -y openssl && rm -rf /var/lib/apt/lists/*
RUN corepack enable
COPY --from=build /app ./
ENV NODE_ENV=production
EXPOSE 3000
CMD ["sh", "-c", "pnpm --filter @invitation-app/api exec prisma migrate deploy && node apps/api/dist/src/main.js"]
```

**Impact :** en cas de compromission applicative (dépendance vulnérable, RCE via une entrée non validée, etc.), le processus a des privilèges root à l'intérieur du conteneur — surface d'attaque inutilement large pour un service qui n'a besoin d'écrire nulle part sur le système de fichiers hors de ses propres logs.

**Correction proposée :** ajouter `USER node` juste avant le `CMD`, après avoir vérifié que l'utilisateur `node` a les droits de lecture sur `/app` (c'est le cas par défaut avec `COPY --from=build`, à condition de ne pas dépendre d'écritures sur des chemins root-only).

**Effort :** S

### [MAJEUR] Le « multi-étapes » ne réduit rien : l'image finale embarque tout le monorepo et toutes les devDependencies

**Où :** `apps/api/Dockerfile:10-34` (les deux étapes)

**Constat :** l'étape `runtime` fait `COPY --from=build /app ./` (ligne 31), c'est-à-dire qu'elle recopie **l'intégralité** du répertoire de build : le code source complet des trois paquets du workspace (`apps/api/src`, `packages/shared/src`, et `apps/web/package.json`), et surtout un `node_modules` installé **sans** `--prod` (ligne 23 : `pnpm install --frozen-lockfile`, sans filtre de production), donc avec les devDependencies des trois paquets — `eslint`, `jest`, `ts-jest`, `@nestjs/cli`, `vite`, `tailwindcss`, `oxlint`, `vitest`, etc. La seule chose qui distingue l'étape `runtime` de l'étape `build`, c'est `ENV NODE_ENV=production` et `EXPOSE 3000` : ni élagage de dépendances, ni copie sélective de `dist/`.

**Preuve :**

```dockerfile
# apps/api/Dockerfile:23-25 — install SANS --prod, pour toutes les dépendances du workspace
RUN pnpm install --frozen-lockfile
RUN pnpm --filter @invitation-app/api exec prisma generate
RUN pnpm --filter @invitation-app/api build
```

```dockerfile
# apps/api/Dockerfile:31 — copie intégrale, aucun tri
COPY --from=build /app ./
```

La raison tient à la ligne 34 : `CMD` invoque `pnpm --filter @invitation-app/api exec prisma migrate deploy`, ce qui nécessite le contexte complet du workspace pnpm (tous les `package.json`, `pnpm-workspace.yaml`, et le paquet `prisma` en devDependency de `apps/api`) pour résoudre le filtre — d'où le besoin de tout recopier.

**Impact :** image de production nettement plus grosse et plus lente à déployer que nécessaire, et surface installée qui inclut des outils de développement (compilateurs, linters, frameworks de test) qu'un attaquant ayant un accès au conteneur pourrait détourner. Ce n'est pas qu'une question de taille : c'est le signe que le choix d'invoquer les migrations via `pnpm --filter` au démarrage a dicté, par effet de bord, de ne jamais réduire l'image.

**Correction proposée :** découpler l'exécution des migrations de `pnpm --filter` — installer `prisma` comme dépendance de production de `apps/api` et invoquer directement `node_modules/.bin/prisma migrate deploy` (ou copier le binaire résolu) sans passer par le filtre du workspace. Une fois ce découplage fait, l'étape `runtime` peut se limiter à copier `apps/api/dist`, le client Prisma généré, et un `node_modules` installé avec `pnpm install --prod --frozen-lockfile` limité au paquet `api`.

**Effort :** M

**Constat :** `app.enableCors({ origin: config.get('FRONTEND_URL') || '...', credentials: true })` n'accepte qu'une chaîne unique. Vercel génère par défaut une URL différente pour chaque déploiement de prévisualisation (branche, PR), qui ne correspondra jamais à la valeur unique de `FRONTEND_URL`.

**Ce qu'il faudrait pour trancher :** dépend d'une décision produit hors de mon périmètre — le projet a-t-il besoin que l'admin puisse se connecter depuis un déploiement de prévisualisation Vercel, ou seulement depuis le domaine de production ? Si seul le domaine de production compte, ce n'est pas un défaut.

**Correction proposée :** si les previews doivent fonctionner, remplacer la chaîne unique par une fonction de validation d'origine (liste blanche de motifs `*.vercel.app` du projet, ou variable d'environnement listant plusieurs origines séparées par des virgules, à parser comme `ALLOWED_ADMIN_EMAILS` l'est déjà).

**Effort :** S

**Correction proposée :** documenter explicitement, dans le README ou dans `apps/web/vercel.json`, quelle version Node doit être sélectionnée manuellement dans le tableau de bord Vercel, pour qu'elle ne dérive pas silencieusement d'un défaut de plateforme.

### [PISTE] `ADMIN_SEED_EMAIL`/`ADMIN_SEED_PASSWORD` ne sont pas couverts par `env.validation.ts` : un oubli au premier déploiement ne produit qu'un log

**Où :** `apps/api/prisma/seed.ts:11-25` · `apps/api/src/config/env.validation.ts:23-41` (schéma complet, ces deux variables n'y figurent pas)

**Constat :** `seed.ts` lit `process.env.ADMIN_SEED_EMAIL`/`ADMIN_SEED_PASSWORD` directement, hors du schéma Joi de l'application. Si absentes, le script les ignore proprement et logue `"ADMIN_SEED_EMAIL/ADMIN_SEED_PASSWORD not set, skipping admin seed"` plutôt que d'échouer.

**Ce qu'il faudrait pour trancher :** ce comportement est cohérent avec le fait que le seed est idempotent et volontairement silencieux pour ne pas bloquer un redéploiement — mais rien ne garantit qu'un opérateur remarque cette ligne dans les logs de déploiement lors du tout premier déploiement, moment où l'absence de compte admin est la plus critique (aucun endpoint d'inscription publique n'existe, par construction du domaine).

**Correction proposée :** à trancher avec l'équipe produit — soit documenter explicitement dans la procédure de premier déploiement qu'il faut vérifier ce log, soit faire échouer le seed en production (`NODE_ENV=production` et variables absentes) si le premier admin n'existe pas encore en base.

**Effort :** S
